# P-256 ECDSA

Signing and verifying with ECDSA over the NIST curve P-256 (secp256r1) and SHA-256, as M17 stream signatures use it
([m17.md](m17.md) section 7). Written from the public standards in section 1 only: no library's code was read or
copied. The protocol's byte formats are in [m17.md](m17.md); this page is the arithmetic, the algorithms, the
encodings, what is secret and what it costs. Which radios carry M17: [feature-matrix.md](../feature-matrix.md).

- Firmware: `core/crypto/p256.c` and `core/crypto/p256_tab.c`, behind the M17 signature switch
  ([build-config.md](../build-config.md)). How they do it, what they cost: section 14.
- Tests: `tests/host/p256Test.c` against the vectors of section 12, plus the M17 vector of [m17.md](m17.md) section 7.5.

## 2. Domain parameters and derived constants

The curve is y² = x³ + a·x + b over GF(p), a = -3, cofactor 1, so every point other than the identity has prime order
n. Values in hex, most significant first (SP 800-186 3.2.1.3).

| Name | Value |
|---|---|
| p | `FFFFFFFF 00000001 00000000 00000000 00000000 FFFFFFFF FFFFFFFF FFFFFFFF` = 2²⁵⁶ - 2²²⁴ + 2¹⁹² + 2⁹⁶ - 1 |
| n | `FFFFFFFF 00000000 FFFFFFFF FFFFFFFF BCE6FAAD A7179E84 F3B9CAC2 FC632551` |
| a | p - 3 |
| b | `5AC635D8 AA3A93E7 B3EBBD55 769886BC 651D06B0 CC53B0F6 3BCE3C3E 27D2604B` |
| Gx | `6B17D1F2 E12C4247 F8BCE6E5 63A440F2 77037D81 2DEB33A0 F4A13945 D898C296` |
| Gy | `4FE342E2 FE1A7F9B 8EE7EB4A 7C0F9E16 2BCE3357 6B315ECE CBB64068 37BF51F5` |

Derived, computed and checked when this page was written (R = 2²⁵⁶, the Montgomery radix of section 4):

| Name | Value | Use |
|---|---|---|
| -p⁻¹ mod 2³² | `00000001` | Montgomery reduction mod p: the per-word factor is the low word itself (also 1 mod 2¹⁶) |
| -n⁻¹ mod 2³² | `EE00BC4F` | Montgomery reduction mod n (`BC4F` mod 2¹⁶) |
| R mod p | `00000000 FFFFFFFE FFFFFFFF FFFFFFFF FFFFFFFF 00000000 00000000 00000001` | 1 in Montgomery form |
| R² mod p | `00000004 FFFFFFFD FFFFFFFF FFFFFFFE FFFFFFFB FFFFFFFF 00000000 00000003` | into Montgomery form mod p |
| R² mod n | `66E12D94 F3D95620 2845B239 2B6BEC59 4699799C 49BD6FA6 83244C95 BE79EEA2` | into Montgomery form mod n |
| p - n | `4319055358E8617B0C46353D039CDAAE` (127 bits) | the verify comparison of section 8 |
| p mod 4 | 3 | a square root is c^((p+1)/4) (only to decompress a point, section 3) |

p - 2 and n - 2 are the inversion exponents (section 4.4).

## 3. Encodings

All integers and field elements are 32 bytes, most significant byte first (SEC 1 2.3.5 to 2.3.8). A value read from
32 bytes is an integer below 2²⁵⁶; each use says which range it must be in.

| Item | Bytes | Form |
|---|---|---|
| Private key d | 32 | integer in [1, n-1] |
| Public key Q, M17's form (key lists, key exchange; M17 never sends a key on air) | 64 | x ‖ y: SEC 1 uncompressed without its `04` |
| Public key, SEC 1 uncompressed | 65 | `04` ‖ x ‖ y |
| Public key, SEC 1 compressed | 33 | `02` (y even) or `03` (y odd) ‖ x |
| Signature | 64 | r ‖ s, each an integer in [1, n-1] |
| Message hash H | 32 | SHA-256 output, used as e = H read as an integer (FIPS 186-5 6.4.1 step 2: len(n) = hashlen = 256, no truncation) |

The identity has no 64-byte form. 64 zero bytes is not on the curve and is refused like any other bad key.

A tool that imports keys accepts the 64-byte, 65-byte and 33-byte forms. The codeplug stores the 33-byte compressed
form ([m17-codeplug.md](m17-codeplug.md) 4). The radio decompresses it (`p256_pub_decompress`, section 14) before it
verifies or checks a key, and compresses Q (`p256_pub_compress`) for the fingerprint and the key check. Decompressing
needs a square root (y = c^((p+1)/4) with c = x³ - 3x + b, then the parity from the prefix; refuse when y² ≠ c).

## 4. Field arithmetic

### 4.1 Representation

A field element is 8 words of 32 bits, least significant word first, in Montgomery form (a·R mod p), always fully
reduced into [0, p). Values enter Montgomery form by a multiply with R² mod p and leave it by a multiply with 1.
The same code does arithmetic mod n for scalars (section 4.5), with its own constants.

Everything that can touch a secret is constant time (section 10): no branch and no memory index depends on a
value. A conditional subtraction is a subtraction whose result is kept or dropped with a mask made from the borrow.

### 4.2 Multiplication

The 512-bit product of two elements takes 64 products of 32 x 32 bits into 64. How the CPU makes one decides the
speed more than anything else:

| CPU | 32 x 32 -> 64 | Notes |
|---|---|---|
| Cortex-M4 | `UMULL`, `UMLAL`, `UMAAL`, one cycle | `(uint64_t)a * b` compiles to `UMULL`. Product scanning (one column at a time, a three-word accumulator) is the plain C form; an assembly version with `UMAAL` is about three times faster and optional |
| C-SKY CK803S | not in the base instruction set | `(uint64_t)a * b` is a call to `__muldi3`. Two ways out, as `core/dsp/fxp.h` describes: the HI/LO multiply unit (`mulu`, then `mfhi`/`mflo`) in a file built with `-Wa,-mdsp`, legal only while one task alone uses HI/LO, since the context switch does not save them; or products of 16-bit halves (`mult` gives the full 32-bit product of two 16-bit values), four per 64-bit product, or 16-bit limbs throughout |

A squaring may share the multiply code; a separate one saves about a fifth.

### 4.3 Reduction mod p

Montgomery reduction (recommended). With -p⁻¹ mod 2³² = 1, each of the 8 rounds takes m = the current low word and
adds m·p, which clears that word. m·p = m·(2³² - 1)·2²²⁴ + m·2¹⁹² + m·2⁹⁶ - m: the -m cancels the low word exactly,
and the rest adds m at word offsets 3 and 6 and the 64-bit value m·(2³² - 1) = (m·2³²) - m at word offset 7 (counted
from the current low word). A round is only word additions with carries, no multiply and no negative intermediate.
The result is below 2p: one constant-time conditional subtraction finishes.
The same rounds reduce mod n with a real multiply for m = t₀ · `EE00BC4F` mod 2³² and m·n.

The NIST fast reduction (SP 800-186 G.1.2) is the alternative for p: from the 16 words A₁₅..A₀ of the product,
B = T + 2S₁ + 2S₂ + S₃ + S₄ - D₁ - D₂ - D₃ - D₄, with the word patterns given there. For a product of two elements
below p, B lies in (-4p, 5p): up to four additions of p when negative, up to four subtractions when ≥ p, each
constant time (masked), and the elements are not in Montgomery form. Random products almost never pass 4p, but real
ones do: x = p - 1 with y = `FFFFFFFE FFFFFFFD FFFFFFFF 00000001 00000001 00000001 00000003 00000004` gives B ≥ 4p
(section 12 has it). Either reduction is fine; choose one and keep it.

### 4.4 Addition, subtraction, inversion

- a + b: add with carry, then subtract p and keep that result when the sum carried or did not borrow.
- a - b: subtract with borrow, then add p masked by the borrow.
- Inversion mod p: Fermat, a^(p-2). p - 2 in bits, most significant first: 32 ones, 31 zeros, a one, 96 zeros,
  94 ones, `01`. An addition chain on runs of ones does it in 255 squarings and 13 multiplications. With xₖ = a^(2^k -
  1): x₂, x₄, x₈, x₁₆, x₃₂ by doubling the run (31 squarings, 5 multiplications); then t = x₃₂ squared 32 times · a;
  t squared 96 times; t squared 32 times · x₃₂, twice; then squared 16, 8, 4, 2 times, times x₁₆, x₈, x₄, x₂; finally
  squared twice · a. Checked against a^(p-2) when this page was written. The exponent is public and the chain fixed,
  so it is constant time.
- Inversion mod n: a^(n-2) with a 4-bit fixed window over the public exponent (about 255 squarings, 64
  multiplications, 14 for the table). Constant time; used for k⁻¹ when signing and s⁻¹ when verifying.

### 4.5 Scalars

Scalars mod n use the same 8-word layout and Montgomery code with the n constants of section 2. Signing needs
k⁻¹, r·d, e + r·d and the product; verifying needs s⁻¹, e·s⁻¹ and r·s⁻¹. A 32-byte value that must be below n is
compared with n in constant time (a full-width subtraction and its borrow).

## 5. Points

Jacobian coordinates (X : Y : Z) stand for the affine point (X/Z², Y/Z³); Z = 0 is the identity. a = -3 makes the
doubling cheap. The formulas are the published ones for short Weierstrass curves with a = -3:

| Operation | Cost (M multiply, S square) | Exceptional inputs |
|---|---|---|
| Doubling | 3M + 5S | none: the identity doubles to Z = 0 by itself, and P-256 has no point of order 2 |
| Addition, both Jacobian | 11M + 5S | P = Q (the formula yields 0 : 0 : 0, must double instead), P = -Q (gives the identity), either input the identity |
| Mixed addition, second point affine (Z = 1) | 7M + 4S | the same |

Variable-time code (verifying, section 8) handles the exceptional inputs with branches. Constant-time code
(signing) computes the addition and the doubling of the first input both and selects, with masks, the addition, the
doubling, the identity or the other input. That adds one doubling per addition and makes the result right for every
input.

Complete projective formulas for a = -3 (Renes, Costello and Batina, 2016, IACR ePrint 2015/1060) have no
exceptional inputs at all, at about 12M per addition and 8M + 3S per doubling: slower, since doublings dominate,
but one formula and no selects. Either choice passes the tests of section 12; the cost table assumes Jacobian.

The affine x of a result is X · (Z⁻¹)², one inversion (section 4.4).

## 6. Scalar multiplication

### 6.1 k·P, constant time (signing)

A fixed window of 4 bits over signed odd digits, so every window adds exactly one table point and no digit is zero:

1. Compute n - k always and keep it in place of k when k is even (a select by mask on k's low bit; n is odd, so the
   kept value is odd), and negate the result's y at the end under the same mask. Signing needs only x(R), which the
   negation does not change; Q = d·G needs it.
2. Recode k into 64 digits: 63 times, dᵢ = (k mod 32) - 16 and k = (k - dᵢ) / 16; the last digit is what is left.
   k stays odd, so every dᵢ is odd in [-15, 15], and the top digit is odd in [1, 15] for every k below n (checked
   when this page was written).
3. The table holds P, 3P, 5P, ..., 15P: 8 Jacobian points (768 bytes).
4. Start from the table point of the top digit. For each lower digit: 4 doublings, then add the table point for |d|,
   negated when d < 0. Every table read, the top digit's too, scans all 8 entries and keeps one by mask; the
   negation is a masked select of y or p - y.
5. Convert to affine.

252 doublings and 63 additions, the same sequence for every k. The two scalars that need care, k = 0 and k ≥ n, are
refused before this (sections 7 and 9). The exceptional additions of section 5 do happen for legal k: k = n - 2 is
odd, its lowest digit is -1, and the last addition adds -P to (n - 1)·P = -P, a doubling. The P256-MULT vectors
k = n - 3 to n - 1 check this.

k·G with a fixed G can use a precomputed affine table in flash and mixed additions (a comb of 4 teeth and 64 rows
takes 1 KB and about 63 doublings and 64 additions, with the masked selects of section 5). It is an optimization;
the general routine with P = G is correct.

### 6.2 u·G + v·Q, variable time (verifying)

Every input of a verification is public, so it may branch. Write u and v in width-5 NAF (digits 0 or odd in
[-15, 15], at least four zeros after each nonzero digit) and interleave them (Straus-Shamir): one chain of 256
doublings, and an addition from G's table or Q's for each nonzero digit, about 43 per scalar. Each table holds the
odd multiples P, 3P, ..., 15P. G's can be affine and constant in flash (mixed additions); Q's is built per
verification. The doubling and identity cases of section 5 happen here for legal inputs (Q = G, Q = -G,
u·G = -v·Q) and must be handled.

## 7. Signing, with RFC 6979 nonces

Inputs: the private key d in [1, n-1] and the 32-byte hash H. M17 hands its stream hash in as H; it is not hashed
again ([m17.md](m17.md) section 7.3). FIPS 186-5 6.4.1 with k from RFC 6979 3.2:

1. e = H as an integer (it may be ≥ n; it enters only mod n).
2. k by RFC 6979 3.2 with hlen = qlen = 256, h1 = H, x = d. HMAC is HMAC-SHA-256; V and K are 32 bytes.
   - V = `01` x 32, K = `00` x 32.
   - K = HMAC_K(V ‖ `00` ‖ d ‖ h), V = HMAC_K(V); K = HMAC_K(V ‖ `01` ‖ d ‖ h), V = HMAC_K(V). Here d is 32 bytes
     and h is bits2octets(H): H mod n as 32 bytes. H ≥ n happens (rarely) and h is then H - n, not H.
   - Loop: V = HMAC_K(V); k = V as an integer. If 1 ≤ k ≤ n-1, done. Else K = HMAC_K(V ‖ `00`), V = HMAC_K(V), loop.
     Compare, never reduce: k is taken or refused whole.
3. R = k·G (section 6.1), r = x(R) mod n. x(R) < p < 2n, so one conditional subtraction.
4. s = k⁻¹ · (e + r·d) mod n.
5. If r = 0 or s = 0, fail. The standards differ here: FIPS 186-5 6.4.1 step 11 says a deterministic k fails,
   while RFC 6979 3.4 calls a k with r = 0 unsuitable and continues the loop of step 2 for the next k. Either is
   acceptable: the chance is about 2⁻²⁵⁶, no test vector reaches it, and failing is the simpler code.
6. Wipe k, k⁻¹, K, V and every intermediate (section 10). Output r ‖ s.

The same d and H always give the same signature. That is the point: no random source is needed, and a k is never
reused for a different H.

**Two-phase signing.** The costly part is R = k·G. FIPS 186-5 allows k, k⁻¹ and r to be computed before H is known
when k is random, and protected like the key. RFC 6979's k depends on H, so it cannot be computed early. A caller
that needs the signature within a few milliseconds of knowing H uses a k from a deterministic random bit generator
instead: RFC 6979's same HMAC process, with h replaced by a value that never repeats for the key (for example the
SHA-256 of a counter kept in the settings store and advanced before use, the transmission's start time and any
entropy the radio has). The signature stays valid; only the test vector's exact r and s are specific to RFC 6979.
Where that is needed is a choice of the protocol code ([m17.md](m17.md) section 12).

## 8. Verifying

Inputs: H, the 64-byte signature, the 64-byte public key. FIPS 186-5 6.4.2:

1. Read r and s; refuse unless both are in [1, n-1]. Refuse the key unless it passes section 9's validation (do it
   once when a key is stored, and again here: it is cheap next to the rest).
2. e = H as an integer.
3. w = s⁻¹ mod n; u = e·w mod n; v = r·w mod n.
4. (X : Y : Z) = u·G + v·Q (section 6.2). Refuse when Z = 0.
5. Accept when x(R) ≡ r (mod n). Without an inversion: x(R) is in [0, p); accept when X = r·Z² (mod p), or, when
   r < p - n, when X = (r + n)·Z² (mod p). The second case is reachable (x(R) in [n, p)) and section 12 has a vector
   for it.

Do not refuse a high s. (r, s) and (r, n - s) are both valid; M17 does not ask for the low-s form, and its own test
signature has s > n/2. A replay cache must key on the signed hash H, not on the signature bytes.

## 9. Keys

**Public key validation** (SP 800-186 D.1.1.1; with cofactor 1 it is also the full validation): x and y in
[0, p-1], y² = x³ - 3x + b (mod p), not the identity. A stored key that fails is refused when it is imported.

**Public key from the private key:** Q = d·G (section 6.1), refusing d = 0 and d ≥ n. The radio may show and export
Q; it never shows or exports d.

**Key generation** needs a random source: FIPS 186-5 A.2.2, rejection sampling (take 32 random bytes; if the integer
is 0 or ≥ n, take new bytes). A radio without a source it trusts does not make keys: the host tools make them from
the PC's random source and load d as a secret. A private key derived from a short passphrase or a callsign is
guessable and is not offered.

## 10. Secrets and side channels

| Value | Secret |
|---|---|
| d, k, k⁻¹, the RFC 6979 K and V, the DRBG state of section 7, every intermediate of k·G and of s | yes |
| H, r, s, Q, u, v, everything in verifying | no |

- Secret values never appear in debug link output, logs, views or the crash record. The debug link shows a key only
  as set or not set, as for other secrets ([channel-modes.md](channel-modes.md) section 8).
- The crash record and the fault trace keep the general registers at the fault (all of r0-r13 on the HR_C7000;
  r0-r3 and r12 on an STM32) and 16 words at the stack pointer ([crash-log.md](crash-log.md)), and they leave the
  radio through the debug link, the report over the air and the host UART. Signing keeps its secrets in one context
  structure outside the stack (the scratch) and wipes it (a write through `volatile`, so it is not optimized away)
  when signing ends, whether it succeeded or not; d itself sits in lent memory next to it, never on a task stack.
  A fault in the middle of the work could still leave secret words in those registers and stack words. Closed: the
  caller brackets signing, the key check and every key read with the secret work count, and while it is not 0 the
  capture zeroes every saved general register and stack word and the trace prints them as zeros
  ([crash-log.md](crash-log.md) 1.4).
- The storage journal holds a copy of the last flash sector rewritten ([settings-store.md](settings-store.md) 4), and
  the debug link's storage dump can read it ([debuglink.md](debuglink.md) 3.13). A write of the codeplug settings
  area while it holds a key (a system secret, such as the M17 signing key, or a traffic key) erases the journal's
  copy once the rewrite is done, and the boot erases any copy left once nothing is to replay (settings-store.md 4):
  no key stays in the dump.
- Constant time for everything secret: the field code of section 4, the select of section 5, the window of section 6.1,
  the inversion mod n by exponentiation. Verification may be variable time.
- Threat model: physical access to a radio gives the codeplug and so the key; this code does not try to stop that.
  What it avoids is leaking d through the output of a working radio: timing, the debug link, a reused k.

## 11. Cost

Counts in field multiplications (M; a squaring is about 0.8 M) with the choices above. Cycles are estimates from
the instruction sequences each CPU's compiler makes at `-O2` for the inner product loop, with about 30 % added for
additions, copies and selects; the build's default is `-Os`, so the estimates assume the P-256 file joins the
Makefile's hot list (`HOT_SRC`, built with `OPT_HOT`). They are not measured: measure them on each platform before a
deadline depends on them.

| Operation | M (about) |
|---|---|
| Inversion mod p | 220 |
| Inversion mod n | 330 (generic Montgomery mod n) |
| k·G, section 6.1 | 3,300 + 220 |
| Sign: k·G, k⁻¹, RFC 6979 (22 SHA-256 blocks) | 3,900 |
| Verify: u·G + v·Q, s⁻¹ | 3,400 |
| k·G with the 1 KB comb | 1,800 |

The time depends on the core clock, which is the board's: radios on the same CPU run at different clocks (168 MHz
and 72 MHz both occur today; each radio's hardware page has its clock).

| CPU, field multiply | Cycles per M | Sign: cycles, at 168 / 72 MHz | Verify: cycles, at 168 / 72 MHz |
|---|---|---|---|
| Cortex-M4, `UMULL` | about 1,000 | 3.9 M: 23 / 54 ms | 3.4 M: 20 / 47 ms |
| Cortex-M4, `UMAAL` assembly field multiply (optional) | about 300 | 1.2 M: 7 / 16 ms | 1.0 M: 6 / 14 ms |
| CK803S, HI/LO unit | about 1,300 | 5.1 M: 30 / 70 ms | 4.4 M: 26 / 61 ms |
| CK803S, 16-bit halves | about 3,000 | 11.7 M: 70 / 163 ms | 10.2 M: 61 / 142 ms |

Memory: a Jacobian point is 96 bytes; the signing table 768 bytes; verifying needs two tables (1.5 KB, or 768 bytes
with G's affine in flash, 512 bytes there) and 10 to 20 field elements of scratch. Run it in one task with this memory in a static
context, not on a small stack. Code: an estimated 5 to 8 KB of Thumb-2, plus 512 bytes for G's verify table
(section 6.2) and 1 KB for the optional signing comb (section 6.1).

### 14.2 Arithmetic

| Part | Choice |
|---|---|
| Elements | 8 x 32-bit words, least significant first, Montgomery form, always below the modulus |
| 32 x 32 -> 64 | Chosen by CPU macro: `UMAAL` on Cortex-M4 (a·b + c + d in one instruction), plain C (`UMULL`) on other Arm cores and the host, four 16 x 16 products on C-SKY (`__csky__`; `FXP_SPLIT16` runs it on the host). No 64-bit value in the C-SKY carry chains: register pairs spill there |
| Product | Operand scanning, 64 word products; squaring 36 (the cross products once, doubled by a shift) |
| Reduction mod p | Montgomery with -p⁻¹ = 1 (section 4.3), summed a column at a time: no multiply, one conditional subtraction |
| Reduction mod n | Generic Montgomery rounds, m = w·`EE00BC4F` |
| Inversion | Mod p: the chain of section 4.4 (255 S + 13 M). Mod n: a 4-bit fixed window over the public n - 2 (253 S + 68 M, the 15-entry table included) |
| Points | Jacobian, a = -3: doubling 3M + 5S, mixed addition 8M + 3S, Jacobian addition 12M + 4S (verify only) |
| k·G | Section 6.1 over the flash table: 64 signed odd digits, 252 doublings, 63 mixed additions. The first 62 additions cannot meet an exceptional input for any valid k (the accumulator is 16m·G with 16 ≤ 16m < n/16 + 16), so only the last is complete: it computes the doubling as well and selects by mask |
| u·G + v·Q | Width-5 NAF of u over the flash table, width-4 NAF of v over Q, 3Q, 5Q, 7Q (Jacobian, built per call), one doubling chain; exceptional cases by branches |
| Verify compare | X = r·Z², or (r + n)·Z² when r + n < p (section 8 step 5) |
| Decompression | c^((p+1)/4) bit by bit (253 S + 33 M), two elements of room |

### 14.3 Constant time

Signing, Q = d·G and RFC 6979 take the same instructions and addresses for every d and k.

- Selects are masks. A mask comes from a 0 or 1 through an empty `asm` the compiler can't see through. The zero test
  is the carry of x + 2³² - 1: with the usual `(x | -x) >> 31` GCC 13 for Arm recognized x ≠ 0 and made a compare and
  an IT block.
- The table read scans all 8 entries. The negation of a table y is a masked select of y or p - y.
- The n - k swap for an even k, the final negation and the last addition's doubling are masked selects.
- The checks of d and k against [1, n - 1] are a borrow chain over the bytes.
- RFC 6979's candidate test is constant time. Its loop takes another round with probability about 2⁻³², and then
  only that a candidate was refused shows.
- Checked in the compiled code, `arm-none-eabi-gcc` 13.3 and `csky-elf-gcc` 14.2, `-Os` and `-O2`: every
  conditional branch in the field multiply and square, both reductions, the additions, subtractions and conditional
  subtraction, the window select, the doubling, the mixed addition and k·G is a loop end on a counter or pointer.
  The others test public values: the recoding's word boundary (loop index), the exit before the last digit, the
  exponent nibbles of the inversion mod n. The only IT block in them is the word-boundary test.
- The host test counts field and scalar multiplies: the same 3,316 per signature for keys and nonces of any weight,
  even or odd.
- Not covered: whether the CPU's multiplier takes the same time for every operand. Cortex-M4 `UMAAL` does. The CK803S
  `mult` is unconfirmed (section 13).

### 14.4 Memory and secrets

| Item | Value |
|---|---|
| Context in the scratch | 1,416 of the 1,536 bytes of `p256_scratch_t`, aligned to 8 inside it (asserted with that room): signing 896, verifying 1,416 (the same on both CPUs) |
| Signing's layout | Product (64), 6 temporaries (192), k, e, r, s, d (160), then by phase: RFC 6979's HMAC, K, V, H mod n (320; 312 on C-SKY); k·G's accumulator, doubling, selected point, odd k and its digits (352); the 15 powers of the inversion mod n (480) |
| Verifying's layout | Product and temporaries (256), u, v, r, the accumulator and a table point (256), then the 15 powers, later Q's table (384) and both NAFs (520) |
| Heap, recursion, RTOS calls | none |
| Wiped | The whole scratch, before every return of `p256_sign`, `p256_sign_k`, `p256_pub_from_priv` and `p256_rfc6979_k`, on success and on failure. A refused signature leaves r ‖ s zero. Verifying handles public values only and leaves them |
| On the stack | Frames and spilled registers only; the HMAC wipes its key block and SHA-256 its message schedule. A caller holding d brackets the work with `crash_secret_enter` / `_leave` (section 10) |

| `p256_sign_k` | 216 | 208 | `sign` 40, `mul_g` 64, `pt_madd` 40, `fe_mul` 16, `mul_wide` 56 |
| `p256_pub_from_priv` | 208 | 196 | the same through `mul_g` |
| `p256_verify` | 208 | 184 | `p256_verify` 72, `sc_inv` 40, `sc_sqr` 16, `redc_n` 56, `cond_sub` 24 |

The P-256 frames stay under 256 bytes. RFC 6979 runs on the shared HMAC-SHA-256, which needs 264 bytes alone on
Cortex-M4 (`hmac_sha256_final` 48, `sha256_final` 40, `sha256_update` 24, `compress` 152). The table's chain goes
from `hmac_sha256_init` into `sha256_final`, which only a key longer than 64 bytes takes; with RFC 6979's 32-byte
key the deepest is `hmac_sha256_final`. Signing therefore needs about 350 bytes of the radio task's stack.

### 14.5 Cost

| Item | Cortex-M4 | CK803S |
|---|---|---|
| Code, `-O2` (`-Os`) | 10,492 (7,990) bytes | 10,094 (7,786) bytes |
| Constants (`p256_tab.c`) | 512 bytes | 512 bytes |
| HMAC-SHA-256 (`hmac_sha256.c`, `-Os`) | 628 bytes | 656 bytes |

Multiplies counted on the host: a signature takes 1,281 multiplies and 1,710 squarings mod p and 325 operations mod n.
A verification takes 1,774 and 1,634 mod p and 324 mod n. Host time, `gcc -O2`, Core i9-9900K: sign 0.25 ms and verify
0.28 ms; with the 16-bit halves 0.50 and 0.56 ms.

The radio times are estimates, not measurements. They come from a static model of the `-O2` code: each instruction a
cost by class, loops by their trip counts, the host's operation counts, 5 % for the code between the calls and 22
SHA-256 blocks for RFC 6979.

- Cortex-M4: 1 cycle per ALU operation and `UMAAL`, 2 per load. A word product is `UMAAL`, a load and a store,
  about 5 cycles with the rows unrolled. A field multiply is about 760 cycles, a squaring 730, an addition 235.
- CK803S: 1 cycle per instruction and per `mult` (assumed single-cycle), 2 per load. A word product is 4 `mult` and
  29 other instructions (adds, carries by compare, the halves, the loads and store, the loop). A field multiply is
  about 2,840 cycles, a squaring 2,100.

| Cortex-M4, 168 MHz | 23 ms | 24 ms | |

A signature runs about 710,000 `mult` on CK803S: each cycle a slower multiplier takes adds 0.7 M cycles. The
radio's own measurement (the M17 signature bench) replaces these figures.

The `UMAAL` build also ran on an emulated Cortex-M4 (QEMU `mps2-an386`, semihosting): `p256Test` and every P-256
vector pass. Counted there with `-icount`, a signature is 2.9 M instructions and a verification 3.0 M. The model's
cycles are about 1.3 times these, since loads and taken branches take more than one cycle. QEMU counts
instructions, not cycles, and has no flash wait states.
